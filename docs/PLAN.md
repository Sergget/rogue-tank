## 3. C 档设计研究：横向卷轴节点（横向推进）—— ⏳ 方案已定、**已降级**（0/4 批次）

> **2026-09-23 用户裁定**：本档降级为 **C 档**——先做 A 档（清账）与 B 档（推进轴玩法），C 档待 A/B 完成后评估（理由见 §4.1）。本节方案与实测数据完整保留、不作废。

**用户设计征询原文（2026-09-21）**：「目前因电脑为横屏，始终无法平衡纵横方向的视差问题。研究：① 能否将地图改为横向卷轴，地图基本为摄像机最大宽度×2、摄像机最大长度×10，作为 1 个地图节点，玩家大体上从左往右推进。生成敌人时不再完全随机，而是按照『防线』的概念，在随机生成的路网路口、密集建筑、河流水体、树林或附近生成一批一批的敌人。敌人渲染范围考虑扩大到略大于触发敌人 engage 的范围；② 成熟后再考虑不局限于横线卷轴。」

**研究结论**：**可行**，但不能靠「把节点尺寸改大」实现——现有生成器把「地图尺寸」与「元素世界尺寸」绑在同一个 `scale` 上，视野圆又被视口窄轴绑架。落地方案 = **横向区块拼装（strip 生成器）**，已用 Node 探针脚本实测验证可通行性（§3.4），两条看似更简单的路径已实测排除（§3.5）。

### 3.2 现状诊断（file:line 证据）

1. **地图尺寸与元素尺寸同源绑定**：`nodeScaleFor`（`js/tank_map.js:193-200`）= `3 × max(vw/模板w, vh/模板h)`，`generateNode` 的 `scale` 同时放大模板尺寸**与**元素世界尺寸（`js/tank_nodegen.js:1634`）。⇒ 地图纵横比必须 ≈ 模板纵横比（700:400 ≈ 1.75）。直接改成 10 屏×2 屏（5:1）会让元素被放大 3 倍以上（建筑 600px+），或地图填不满。
2. **视野圆被窄轴绑架 —— 用户所说「纵横不平衡」的代码根因**：`visionRadiusForViewport`（`js/tank_camera.js:119-143`）取 `R = screenRadiusRatio × min(vw,vh)/2 ÷ zoom`，横屏下窄轴 = 高度。实测（`triggerDistForDifficulty` = 780，engage 上限 = 520×1.25 = 650）：

   | 视口 | R(zoom=1) | R/触发距离 | 屏幕半幅（横/纵） |
   |---|---|---|---|
   | 1280×720 | 360 | **0.46** | 640 / 360 |
   | 1920×1080 | 540 | **0.69** | 960 / 540 |
   | 2560×1440 | 720 | 0.92 | 1280 / 720 |
   | 3440×1440 | 720 | 0.92 | 1720 / 720 |

   ⇒ 横屏下**敌人在可见之前就已激活、甚至已进入开火距离**（engage 650 > R 540），且横向「屏幕内却看不见」的盲区随宽高比增大——几何必然，调参平衡不了（与 #H1/#H5 的轴向等距诉求同源，但 #H5 的屏幕相对口径使 R 随窄轴缩水）。
3. **生成/结算无「推进轴」概念**：`makeNode` 以玩家出生点为原点按扇区环带撒簇（`js/tank_map.js:288-344`，P-46）；`reinforcementTick` 落点约束为「视口外扩 120px 外 + 距玩家 ≥ 触发距离×1.05」（`js/tank_map.js:790-812`）⇒ 玩家后方同样刷兵；节点完成条件是击杀配额（`tank_mvp.html:3028-3036`）。
4. **已有横向推进的先验（利好消息）**：玩家出生在 `w×0.10` 左缘（`js/tank_map.js:247`）；Boss 生成在 `w×0.7`（`tank_mvp.html:1184`）；路网端点严格落在节点边界线上（`specs/map.md` §3.1）⇒ 片与片天生可首尾相接。

### 3.3 方案骨架：strip 生成器（K 片拼接）

1. **片（chunk）** = 一个现有模板实例，**片内 `scale` 沿用现状口径**（元素尺寸与正式游戏一致，这是可行性的关键——见 §3.5 反面实测）。
2. 沿推进轴首尾相接 K 片（每片宽度 = 模板 w × scale），片间 x 偏移累加。
3. **接缝净空（必需）**：片边界 ±300px 内移除 `structure`/`foliage` 元素（保留 `ground`/`liquid`），否则接缝处通道卡死（实测 4px < 车体宽 38px，§3.4）。
4. **横向贯通干道约束（必需）**：实测 6 个 seed 中约半数节点是**纵向**贯通路（左右边界端点数 0~2），接缝处无路可续；须对横向节点强制「每片含一条横向贯通干道」（`placeRoadNetwork` 拓扑约束或参数化）。
5. **纵向裁剪到目标高**：丢弃片上下边缘元素（实测可行，代价是密度下降，需 §3.6 补偿）；**不做纵向压缩**（实测会挤坏通道，§3.5）。
6. **地面层分块烘焙**：`bakeNodeGroundLayer`（`tank_mvp.html:3633-3634`）现按 `cv.width = node.w` 建整图离屏画布——12.3 屏 = 23640px → RGBA **223MB**；按「最远缩放」口径可达 43000×3600 = **619MB**，必崩。改为按片（tile）烘焙 + 视口内按需 blit。

### 3.4 实测：拼接可行（1920×1080，4 片，`nodeLayoutMetrics`，车体宽 38px 为通行硬门槛）

| 变体 | 尺寸（屏） | covers（实体/road） | 覆盖率 | 连通性 | 最窄通道 |
|---|---|---|---|---|---|
| 单片（现状参照） | 3.0×3.3 | 162 | 0.047 | 1.000 | 36px |
| 直接拼接 | 12.3×3.4 | 546（106/428） | 0.041 | 1.000 | **4px ✗ 卡死** |
| ＋接缝净空 ±300px | 12.3×3.4 | 530（90/428） | 0.036 | 1.000 | 34px ✓ |
| ＋纵向裁到 2.2 屏 & 净空 | **12.3×2.2** | 443（83/350） | 0.054 | 1.000 | 34px ✓ |
| ＋净空加宽到 ±500px | 12.3×2.2 | 432（72/350） | 0.046 | 1.000 | 34px ✓ |

⇒ 结论：拼接 + 接缝净空 + 纵向裁剪 = 连通性 1.000、通道 34px（≈单片 36px），**方案成立**；净空加宽到 ±500 无额外收益（只掉密度），±300 即可。

### 3.6 风险清单（实施前必读）

1. **地面预烘焙内存**：见 §3.3 第 6 条（必须分块）。
2. **接缝**：净空 + 横向贯通干道两项缺一不可（§3.3 第 3/4 条；实测证据 §3.4/§3.5）。
3. **遍历成本**：covers 162 → 443~1200（12 屏）。每帧 O(covers) 的点：draw 视口过滤、**小地图全量遍历**（`js/tank_minimap.js:73-88`）、**AI 避水（每敌每帧）**（`js/tank_ai.js:650`）、`resolveCoverCollisions`。建议按片做空间分桶，只扫邻近片。
4. **密度不足**：裁到 2.2 屏后 83 实体 / 12.3 屏 ≈ **6.7 个每屏**（现状 ≈13 个每屏）⇒ 需密度补偿（片内叠加建筑/森林相位，或把边缘元素钳制回界内而非丢弃）。
5. **小地图**：12.3:2.2 等比缩进 200×200 框会退化成 ~36px 细线（`js/tank_minimap.js:15-19`）⇒ 需改「横向条带 + 视口窗口」布局。
6. **结算与增援语义**：现状 `quotaDone || (noEnemies && !canReinforce)` 与推进正交；增援落点「视口外」会把兵刷在玩家后方 ⇒ 改为「只在前方未清空防线补给」，并引入「抵达右端出口 + 防线清空」的完成条件。
7. **测试重锚**：`scripts/test-map.js:105-109`（节点宽高 ≥3 倍视口断言）、`test-nodegen-calibration.js` 基线表、`test-replay.js` hash、`test-nodegen.js` 七条护栏、4 条 browser 链均会漂移。

## 4. 2026-09-23 路线裁定：A 清账 → B 推进轴玩法（C 档延后）

### 4.1 为什么不是直接上 C 档

- C 档一次性承担三项高风险（§3.6 第 2/7 条）：测试重锚（`test-map` 尺寸断言 / `test-nodegen` 七护栏 / 校准基线 / `test-replay` hash / 四链）、整图地面烘焙内存（12.3 屏宽 ≈223MB RGBA）、covers 162 → 443~1200 的每帧遍历成本（绘制过滤 / 小地图 / AI 避水 / 碰撞）。宜在 B 档验证生成与结算语义之后再评估。

### 9.1 条目 1 · C 档 strip：上下行间接缝渐变（已修复）

**用户口径**：「生存模式下，上下 2 个地图分片间似乎没有渐变过渡，解决后审核还有哪些内容没有实现」。

**根因**：`js/tank_battledraw.js` 的 `drawGround` 里，biome 过渡带**只沿相邻 zone 的公共
`x` 边界**绘制（左右相邻），完全没有处理 `y` 方向。而多行片（`opts.chunkRows >= 2`，
生存模式取 2）的地貌交界正是**上下两行**⇒ 行与行之间是硬切色块。

**修复**：抽出 `drawSeam(axis)` 按轴分派，`x` 与 `y` 各跑一遍。
`y` 方向判据与 `x` 完全对偶（`x` 区间相接/重叠 + `y` 边界相等），过渡带几何同样对偶。
两个方向都用「公共边界 + 区间交集」判据，**对角相邻不会误画**。

**测试同步**：`test-render.js` 的 ⑨f「2 维 zone 分区正确」原在分界 ±60px 采样，
而过渡带半宽 260px ⇒ 采样点落在渐变内、两侧被混合。改为在 ±150px 采样并验证
**色彩方向性**（上侧雪色偏冷、下侧沙色偏暖），既证分区正确、也顺带证交界有过渡。
实测：上 `rgb(198,204,206)` 冷 / 下 `rgb(213,191,141)` 暖。

**C 档剩余未实现项**（审核结果，均属设计取舍而非缺陷）：
- **分块地面烘焙** → 已由**视口锚定滚动烘焙**替代（`drawGroundCached`，每帧 blit 1 次），
  原方案的「按 tile 烘焙 + 视口内 blit」在效果上等价且实现更简单，**不需要再做**。
- **空间分桶** → 已实现（战斗/生成双空间索引）。
- **小地图条带化** → 已实现。
- **推进式结算（B 档③）** → 已沿用在常规节点；生存模式按波次清空，不需要推进轴。
- **strip 密度/难度校准重锚（原 batch 4）** → **仍未做**。属数值校准而非功能缺失；

### 9.2 条目 2 · 敌军弹种难度联动（已实施）

**用户口径**：「进入，敌人等级每提升 3 个等级，敌人可用的弹种也跟随升一级，且除了 boss，
其他敌人只使用 ap 链的弹种」。

**此前状态**：敌军**从不设置 `ammoKey`**，`tank_fire.js` 的 `getAmmoCfg` 兜底成
`RULES.ammoTypes[k] || RULES.ammoTypes.ap` ⇒ 全部敌军恒定打 AP，难度对弹种零调制。

**实现**（`js/tank_model.js`，纯函数可 Node 测试）：
```js
const AP_AMMO_CHAIN = ['ap', 'apcr', 'apds', 'apfsds', 'apfsds_ad'];
enemyAmmoKeyForLevel(lv) { step = floor((lv-1)/3); return AP_AMMO_CHAIN[min(step, 4)]; }
applyEnemyAmmoByLevel(tank, level) { tank.ammoKey = enemyAmmoKeyForLevel(level); }
```
实测：lv1~3→`ap`，lv4~6→`apcr`，lv7~9→`apds`，lv10~12→`apfsds`，lv13+→`apfsds_ad`；
lv1~30 全部落在 AP 链内、等级递增档位单调不降。

**接线**（4 处生成点，全部走同一个 `applyEnemyAmmoForNode(t, node)` 助手）：
节点敌军（`configureTank`）、生存波次、增援、Boss 召唤物。
**Boss 本体显式跳过**（`if(t.isBoss) return`），仍可自由配任何弹种。

**难度→等级换算**：节点只有 `difficulty ∈ [0.15, 0.95]`，无显式 level 字段。
取 `enemyLevelForDifficulty(d)`：线性映射到 **1~13 级**（0.15→lv1、0.95→lv13），
正好覆盖 4 档升级。首节点 `ap`、中后期逐步升到 `apcr`/`apds`/`apfsds`。
