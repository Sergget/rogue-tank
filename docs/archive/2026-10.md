#### #J1. 地雷在 1 个节点内只能部署 1 次

**用户反馈**：「地雷在 1 个节点内似乎只能部署 1 次」。

**根因**：`RULES.abilities.deploy_limits.mineMax`（**场上同时存在**的地雷数上限）恰等于单次雷场数量 `mineFieldCount`（均为 3），首轮雷场即把上限用尽；而地雷存续 30~45s、单节点战斗远长于此 ⇒ 后续雷场全部被 #F6 的「超限拒绝」判据拒收。

**证据**：`js/tank_rules.js` `deploy_limits.mineMax: 3` 与 `mineFieldCount: 3`；`tank_mvp.html` `mineFieldCountNow()` 的余量裁剪 `clamp(count, 0, cap − existing)` 在首轮后恒为 0。

**修复**：`mineMax` **3 → 6**、`mineMaxHardCap` **8 → 12**（`mineFieldCount` 保持 3）。
**口径澄清**：`mineMax` 是**同时在场数**，不是「本局总数」；调大它才能让一个节点内连续布设多轮。

**回归**：`scripts/test-rework-r2.js` #J1 段（`mineMax > mineFieldCount`；连布 2 轮各 3 枚后正好占满上限；满上限时数量为 0 且已布地雷不变）；`test-browser-r4.cjs` F1 段（同节点连续 2 轮无清理；实测 3 枚 → 6 枚）。

#### #J2. 获得电磁炮后再获得其他主炮，会继承「可穿透弹药」特性

**用户反馈**：「获得电磁炮后再获得其他主炮，似乎会继承可穿透弹药的特性」。

**根因**：`js/tank_cards.js` 主武器 `install` 用 `Object.assign({}, 旧 stats, ef.statOverrides)` 合并 —— **旧武器的专有键被一并带进新武器**。最典型的是 `railgun` 的 `pierce` / `pierceDmgMul`（`js/tank_fire.js firePrimaryShell` 据此赋予弹体贯穿能力），于是换上任何其他主炮后仍能贯穿两辆坦克。

**证据（浏览器实测）**：装 `weapon_primary_railgun` 后 `stats.pierce = 1`；再装 `weapon_primary_double_barrel` 后 `type` 已变 double_barrel，但 `pierce` 仍为 1、`pierceDmgMul` 仍为 0.6。

**修复**：换型安装时**先重置 stats 为新类型基准**（`getWeaponDefaults('primary', wType)`）再合并卡牌覆写；同型安装保持原合并语义（幂等，不丢 `tanks/*.json` 自定义数值）。副武器 install 原本就用 `getWeaponDefaults` 构造新对象，无此缺陷；两条路径现共用新增的 `_weaponDefaultsResolver()` 惰性依赖解析器。

**回归**：`scripts/test-cards.js` #J2 段（railgun 引入 pierce → 换 standard/double_barrel 后 `pierce`/`pierceDmgMul` 均为 `undefined`；同型重复安装仍是合并语义）；`test-browser-r4.cjs` F2 段。

#### #J3. 改为全屏幕渲染敌人，取消视野距离计算

**用户裁定**：「改为全屏幕渲染敌人，不再计算视野距离的问题。敌人 AI 是否被触发维持为距离 + 是否有直线视野（建筑或草丛、树冠等）」。

**原缺陷（视野圆体系的三个自相矛盾）**：① 圆心/视口不同源导致「敌人看起来在屏幕内却被隐形」（#K1 曾专门修过一轮）；② **看得见却打不中** —— 炮弹命中同样按该圆剔除（`tank_fire.js` 的 `hiddenByVision` 钩子）；③ 玩家每局都要重新适应一条看不见的边界（#D2 专门画虚线圈来暴露它）。

**修复（整体退役，不留死开关）**：删除 `js/tank_camera.js` 的 `visionRadiusForViewport` / `visionCenter` / `visionClamped`；`tank_mvp.html` 的剔除逻辑（`entityHiddenByVision` 保留同名函数恒返回 `false` 以兼容调用点）、视野虚线圈、`visionRadiusEff` 的卡牌加成与屏幕相对计算；dev 面板「无视野」开关（`tank_devpanel.js` + mvp/bench 接线 + `types/globals.d.ts`）；两张视野卡 `support_commander_periscope`（+15%）与 `sniper_commander_sight`（+25%）按 2026-09-23 A 档死效果卡先例整体删除，`tank_cards.js` 的 `PASSIVE_KEYS` 移除 `commander_sight`（卡池 168 → 166）。

**现行口径**：敌对实体一律渲染、一律可被命中，只剩 `aabbInView` 视口剔除（纯性能）。`RULES.vision` 仅作历史配置留档。

**明确不受影响（用户要求的第二半）**：敌人 AI 接战判定一直是 **「距离 + 直线视野」** —— `RULES.ai.engageRequiresLoS` + `js/tank_ai.js` 的 `hasLoS`，遮挡由 `js/tank_cover.js hasLineOfSight` 按掩体的 `vision: true` 键判定（建筑/岩石/树/灌木/倒树遮视线；栅栏/沙袋/残骸/水/泥/路不遮）。

**回归**：`scripts/test-camera.js` 删除原 #H5/#K1 视野圆断言段（被测对象已不存在），保留 `aabbInView` 与 `minZoom`；`test-browser-smoke.cjs` P-39 段改写为**退役断言**（`visionRadiusEff` 恒为名义常数、不随 zoom 补偿；无隐藏实体）；`test-browser-r4.cjs` F3 段。

#### #J4. 导弹无法发射（激活后零反馈）+ 卡面未写明「伤害跟随 HEAT」

**用户反馈**：「导弹无法发射（卡牌描述中看起来似乎没有按计划中的跟随 heat 伤害值）」。

**核实（浏览器实测，两种情况都成立）**：
- **导弹本身能发射** —— 条件是「炮塔 ±30° 扇形内、600px 射程内、持续锁定 1s」，实测对准后 `shots:1` 正常发射。
- **真缺陷 = 激活后零可见反馈**：`_missileActivated` 激活后 UI 上**没有任何指示**（锁定指示器只在 `_missileLock` 存在时绘制）。玩家按 F 后若炮塔没对准或目标在射程外，导弹既不发也不提示 → 体感「导弹无法发射」。
- **附带状态残留缺陷**：`_missileActivated` 是**开关态**，换掉副武器时未复位（主循环的 `type==='missile'` 门控只是不再推进它）。实测「B3 段激活 → 换成布雷器 → 再装回导弹」会在玩家没按 F 的情况下**自动索敌并发射**。
- **卡面与实现不符**：代码实现了「伤害跟随当前 HEAT 弹种系数」（`getEffectiveHeatAmmoKey` → `computeAmmoConfig` → `dmg = round(base × ammo.dmg + ammo.dmgAdd)`），但卡面只写「伤害 140」，未提该机制，也未写锁定流程。
- **规格自相矛盾**：`specs/combat.md` §4 原写「手动击发沿光标方向直飞（`target=null`，不再自动寻的）」，与 §8.2 的「激活→锁定→自动发射」互相冲突（§4 是 #A21 时期旧口径，未随 #E5 更新）。

**修复**：
1. **HUD 状态反馈**：`btnF` 角标显示「索」（已激活未锁定，琥珀脉动 `.lock-hunting`）／「n%」（锁定中，绿色 `.lock-on`）；`title` 写明锁定条件。
2. **一次性原因提示**：激活后 0.6s 仍无目标 → 提示缺少哪一条（`射程内没有敌对目标` / `炮塔需指向目标 ±30°`）。
3. **激活日志写明条件**（扇形角 / 射程 / 锁定耗时）。
4. **状态残留修复**：副武器换装时复位 `_missileActivated` / `_missileLock` / 提示标志（`js/tank_cards.js` secondary install）。
5. **卡面同步**：`weapon_secondary_missile.json` 与 `weapon_secondary_missile_upgrade.json` 写明「按 F 激活索敌 + 锁定条件 + 装填」，并注明「实际伤害跟随当前 HEAT 弹种升级」。
6. **规格消歧**：`specs/combat.md` §4 改为现行口径并标注 #A21 旧口径已作废。

**回归**：`test-browser-r4.cjs` F4 段（换装后激活态已复位；无目标 → 角标「索」+ lock-hunting；日志说明原因；对准 → lock-on 百分比 + 成功发射）。

#### #L2 精灵炮管安装点系统性偏移，5 车全部偏后（2026-10-06 核实）

- **现象**：`sprite.enabled:true` 时炮弹出膛点与炮口火焰出现在贴图炮管**前方**，偏差 1.94~8.00 模型单位（hummel 最大，约 0.73m）。
- **核实结论**：设计器「按多边形自动对齐」用**未经 axis 归一化**的炮塔原始顶点 `maxX×0.8` 写 `barrel.mountDx`（`designer.js:1060-1069`），而运行时炮塔前缘口径是 `turretFrontDist()`（`js/tank_geometry.js:554-576`），基于**已减去 `axis.dx`** 的顶点（`js/tank_model.js:468`）。两者不同源 ⇒ 偏差随车而异。弹道/炮口火焰取 `gunRoot()/gunTip()`（`js/tank_fire.js:91`），故与贴图炮管错位。
- **证据**：真实模块解算（`mountDx − embed` 应为 `turretFrontDist`）——

  | 车 | turretFrontDist | 当前 mountDx | 应为 | 偏差 |
  |---|---|---|---|---|
  | tiger-I | 15.70 | 15.76 | 17.70 | −1.94 |
  | panzer-IV | 14.00 | 11.20 | 16.00 | −4.80 |
  | hummel | 14.00 | 8.00 | 16.00 | −8.00 |
  | Leapard_1 | 15.90 | 14.32 | 17.90 | −3.58 |
  | Obj 780 | 19.80 | 18.24 | 21.80 | −3.56 |

- **复现**：`node` 载入 `js/tank_model.js applyTankConfig` + `js/tank_geometry.js turretFrontDist`，对比 `tanks/<id>.json` 的 `sprite.barrel.mountDx − embed`。
- **修复方向**：① 设计器自动对齐改用与运行时同源的炮塔前缘口径（`turretFrontDist` 等价算法，即按 `axis` 归一化后取过中轴前缘交点）；② 修正 5 车 `mountDx`。
- **状态**：已修复（§4.54）——`turretFrontDist` 抽出纯函数 `frontDistFromVerts` 导出，设计器换算运行时帧后取 `mountDx = frontDist + embed`；5 车 JSON 重算。复测 Δroot=Δtip=0.000（全 5 车）。
