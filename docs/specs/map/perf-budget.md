## 降级优先级与红线

`tank_3d.html` 是自研 WebGL1 渲染器（`js/tank_render3d.js`：无阴影、无后处理、批几何 + 一次 `drawScene`），所以性能预算不在「花哨特效的开关」，只在四个旋钮上：① 渲染分辨率 ② 粒子总量 ③ 动态几何每帧重建量 ④ 静态几何重建频率。**①②④ 是本页的旋钮**；③ 不在档位表内——动态几何在三个档位下都是每帧全量重建，档位只调分辨率、粒子与炮弹上限。

降级按**玩家感知从低到高**排序，先降前者：

| 顺序 | 手段 | 玩家看到什么 | 为什么排这个位置 |
|---|---|---|---|
| 1 | 渲染分辨率（`resolutionScale`） | 画面变糊 | 可读性、命中判定、操作精度**全不变**；填充率是 GPU 最直接的减负项，HUD 是 DOM 完全不受影响 |
| 2a | 粒子预算 · 环境氛围（`dustIntervalS`） | 履带扬尘变稀 | 扬尘只是位移的替代反馈，稀了仍看得出「车在跑」 |
| 2b | 粒子预算 · 战斗反馈（`particleCap`） | 命中火花/开火烟被裁 | 这是「打中了」的确认，只能在氛围先砍完还不够时动 |
| 3 | 静态几何重建频率（`staticRebuildIntervalS`） | 楼倒下到变成残骸的那一下 | 玩家只在楼塌的瞬间看得出差别 |

**第三优先级的现状（已按档生效）**：`staticRebuildIntervalS` 已在 `RULES.perf.tiers` 里逐档赋值——`high` 0.25 / `mid` 0.40 / `deck` 0.60，`getTierConfig` 原样透传，页面按当前档节流。取值理由：掩体被打烂时页面要重新生成整张 `staticMesh`，是 O(掩体数) 的几何生成——一次齐射同时打掉 3~4 栋楼会连着重建成帧尖峰。间隔只影响「楼倒下的画面更新得多快」，玩家几乎看不出来；但拉长能显著削掉这个尖峰。`high` 0.25 = 接线前的原值（不借降级偷偷改 high 的画质），`deck` 0.60 仍能在半秒内看到楼变成残骸。页面读 `perfCfg.staticRebuildIntervalS || 0.25`，其中的 `|| 0.25` **只是旧缓存规则文件的兜底**，不是现行缺省值。

**红线（绝不降级）**：模拟步长（固定 1/120）、输入采样、HUD 刷新频率、炮弹碰撞判定、AI 决策频率。

| 红线项 | 为何不能降 |
|---|---|
| 模拟步长 1/120 | 120Hz 步长是命中精度与穿深结算的前提 |
| 输入采样 | 降了就变输入延迟，手感当场崩 |
| HUD 刷新 | 已是最低频（每 150ms 一次），再降等于信息缺失 |
| 炮弹碰撞判定 | 降了是玩法不公，不是掉帧 |
| AI 决策频率 | 决定敌人反应是否可信，降了像开挂 |

另一个理由是它们**本来就不是瓶颈**：60fps 下每帧只跑 2 次 `update(1/120)`，HUD 每 150ms 一次。降级只能动**表现**，不能动**模拟**。

## 三档参数表

这张表回答「三档各自长什么样、五个键各取多少」。数值唯一口径是 `RULES.perf.tiers`，本表只是它的现行快照。

| 档位 | 定位 | `resolutionScale` | 1080p 基准下的实际渲染分辨率 | `particleCap` | `dustIntervalS` | `maxShells` | `staticRebuildIntervalS` |
|---|---|---|---|---|---|---|---|
| `high` | 1080p 目标机（G1 验收门基准档） | 1.0 | 1920×1080 | 420 | 0.09 | 40 | 0.25 |
| `mid` | 降一档，战斗反馈全保留 | 0.85 | 1632×918 | 260 | 0.14 | 32 | 0.40 |
| `deck` | Steam Deck / 核显 | 0.7 | 1344×756 | 160 | 0.20 | 24 | 0.60 |

**五键的取值依据**

- `particleCap`：本机复刻本页四个发射点、按真实装填 1.4~2.6s 做 90s × 60 次蒙特的实测——开局 W1（6 车）稳态 ≈72、峰值 85~150；末期 W3（9 车）稳态 ≈150、峰值 150~255；全员贴满射速的极限 ≈295。`high` 取 420 ≈ 极限峰值 +40% 余量；`mid` 取 260 ≈ W3 合围峰值上界；`deck` 取 160 ≈ `high` 开局量级。cap 是「防几何无界增长」的硬天花板，**不是**常规裁剪线——压到 300 会先砍在合围高潮，正好违反降级优先级。
- `dustIntervalS`：`high` 的 0.09 等于接线前 `updateTankVisual` 的硬编码值（≈11 颗/秒/车，life 0.7 ⇒ 单辆存活 ≈7.8 颗）；`mid` 0.14（单辆 ≈5 颗，仍远短于人眼连续感的融合窗）；`deck` 0.20 是「扬尘还在但不密」的下限，彻底关掉会让高速行驶失去速度感（3D 切片没有履带痕迹，扬尘是唯一位移反馈）。
- `maxShells`：弹速 ~600px/s、战场对角 1656px ⇒ 单发在飞 1.5~2.7s；9 车 × 0.5~1s 一发 ≈ 9~18 发同时在飞，`high` 40 留 2 倍余量，`mid` 32、`deck` 24 逐级收紧。超限丢**最老的**——它已远离炮口、飞向的背景里本来就有同名曳光。炮弹本身是威胁可见性的一部分，砍过头等于降难度感知。
- `resolutionScale`：`high` 1.0 必须等于「接线前」的画质，否则降级没有对比基线；`mid` 0.85 是玩家最不易察觉的第一档（像素量 −28%）；`deck` 0.7 是「还认得出是坦克」的下限（再低炮塔环/装甲倾角就读不出来），对 1280×800 的 Deck 原生宽度也是整数像素对齐。
- `staticRebuildIntervalS`：静态几何重建的观察间隔（秒）。掩体被打烂时页面要重新生成整张 `staticMesh`，是 O(掩体数) 的几何生成——一次齐射同时打掉 3~4 栋楼会连着重建成帧尖峰。间隔只影响「楼倒下的画面更新得多快」，玩家几乎看不出来；但拉长能显著削掉这个尖峰。`high` 0.25 = 接线前的原值；`deck` 0.60 仍能在半秒内看到楼变成残骸。

## 门控参数表

这张表回答「什么时候降、什么时候升、中间怎么防抖」。参数同样在 `RULES.perf`，页面不自带阈值。

| 参数 | 值 | 含义 | 取值理由 |
|---|---|---|---|
| `emaAlpha` | 0.12 | 帧时间 EMA 系数 | 时间常数 ≈ 8.3 帧（60fps 下 ≈140ms）：30ms 尖峰只把 16ms 的 EMA 推到 17.7ms（不到 22ms 门槛），真实劣化 ~0.3s 内显形。α=0.3 会被 GC 单帧带走，α=0.05 对 2s 级劣化太钝 |
| `dropAboveMs` | 22 | 持续超过就降级（45fps 地板） | 16.7ms 是 60fps 的理论预算，但浏览器合成 + GC 要吃掉 3~5ms，「稳 60」实际要求 ≤14ms；22ms 已掉到 45fps 以下，此时「降画质换流畅」收益更大 |
| `raiseBelowMs` | 14 | 持续低于才考虑回升 | 与 `dropAboveMs` 留 8ms 迟滞带（防抖第一道闸）；14ms 对应「稳 60 且有余量」 |
| `dropAfterSeconds` | 2 | 超预算持续多久才降 | GC、切地图、首帧 shader 编译都会瞬时 >22ms，不留滞后会当场误降；2s 又短于一次交火 |
| `raiseAfterSeconds` | 8 | 富余持续多久才升 | 降级是救火要快、回升是加负担要保守；8s ≈ 一次喘息期（`RULES.encounter.breatherSeconds`=12s）的大半，避免波次间隙回升、下一波开打又掉回去形成锯齿 |
| `minTierHoldSeconds` | 3 | 升降后至少锁定多久 | 改分辨率会触发 framebuffer 重分配（一帧 hitch），EMA 因此在切换后短暂失真；3s > `dropAfterSeconds`(2)，保证每次降级能被稳定观察 3s 再决定下一步 |

## 逐级升降与抖动抑制

- **只能逐级升降，不跳档**：`high ⇄ mid ⇄ deck`，不许 high→deck 一步到底，也不许 deck→high 一步回顶。跳档会让画面质量突变，玩家会以为渲染坏了。
- **三重防抖**，缺一不可：① 8ms 迟滞带（22 / 14）挡住门槛附近的来回；② 持续时间门槛（降 2s / 升 8s）挡住 GC、shader 编译这类瞬时尖峰；③ 最短驻留 3s 挡住「改分辨率 → hitch → EMA 更差 → 再降」的连环抖。
- **回升比降级保守**：降级只需 2s，回升要 8s。波次间隙（`breather`）恰好是富余最容易出现的窗口，8s 门槛让它升不回去，避免「喘息期升、开打又降」的锯齿。
- **每帧一次 `updateGovernor(gov, rawDt)`**，在 `render()` 之后、`requestAnimationFrame` 之前调：返回的档位作用于**下一帧**，否则会出现「本帧按旧尺寸画完、却按新档位裁粒子」的半帧状态。
- **喂原始 rAF delta**：不喂页面钳位后的值（`if(dt>0.2) dt=0.2` 会把「切后台回来」退化成 0.2s，白推进降级计时），也不喂 `timescale` 缩放后的值（终局冻结时是 0，会被当异常帧全部丢掉）。
- **只有档位真的变了才改画布尺寸**：`applyRenderScale` 先比对当前 `canvas.width/height`，相同直接返回，避免每帧重分配 framebuffer。

## 基准分辨率的取法

**基准分辨率**（`BASE_RES`）= 未降级时画布应有的像素尺寸；实际渲染 = 基准 × 档位 `resolutionScale`。

| 场景 | 取法 | 理由 |
|---|---|---|
| 无 `?w=&h=` | `innerWidth × innerHeight` → 按 `RES_MAX_PIXELS`（1920×1200）**等比**收缩 | 画布被 CSS 的 `100vw/100vh` 拉满视口，基准比例必须与视口一致，否则画面**非等比拉伸**（1280×800 视口下纵向 ×1.111，圆掩体变竖椭圆）。等比收缩防止 4K 视口按 4 倍填充率渲染 |
| 有 `?w=&h=` | 钉死为该值，不跟随视口 | 基线截图、A/B 对照、三档性能测试都要求尺度可复现；这些用例的 viewport 本来与参数一致（720p/1080p/Deck），所以钉死不会引入变形 |
| 视口变化 | 250ms 防抖后重算（仅未钉死时） | 拖拽/全屏会把 CSS 盒子改成新视口尺寸，不重算就回到拉伸状态。防抖是因为每次改尺寸都要重分配 framebuffer，连续触发会拖出可见卡顿 |

**为什么上限是 1920×1200**：4K（3840×2160）填充率是 1080p 的 4 倍，而 CSS 早已把画布拉满——收缩后只是清晰度降低，玩家几乎看不出差别，中低端 GPU 却能因此守住 30fps。2.30M 像素同时覆盖「1080p 满血」与「16:10 有余量」两种常见视口，因此常见屏幕上 `s = 1`、不会被无谓降采样。

**测试钩子**：`__TEST3D__.perf()` 返回 `base`（当前基准）、`baseAuto`（是否跟随视口）、`viewport`（当前视口），三个值共同支撑「钉死尺度」与「等比例」两种断言的区分（见 `scripts/test-browser-perf.cjs` 第 4 组）。

## 页面入口

三个 URL 参数都在 `tank_3d.html` 读，互不依赖。

| 入口 | 作用 | 细节 |
|---|---|---|
| `?w=&h=` | 钉死**基准渲染分辨率** | 缺省跟随视口（见上节）；`w≥320 且 h≥240` 才生效。实际渲染分辨率 = 基准 × 当前档 `resolutionScale`；CSS 撑满视口，所以缩放只影响清晰度，不影响布局与判定 |
| `?tier=` = `high` / `mid` / `deck` | 指定**起始档位** | 非法值回退 `RULES.perf.startTier`（`high`）。**不做设备嗅探**——UA 嗅探在桌面浏览器上不可靠，且会把同一台机器判成两个档 |
| `?perf=manual` | 冻结自适应 | 真实帧不参与档位，只吃测试喂的帧时间 |

**`?perf=manual` 为什么必须有**：软件渲染（CI 的 swiftshader）帧时间动辄 80ms+，真实帧会把档位一路打到 `deck`，「逐级降 → 逐级升」的阶梯断言就永远测不到 `mid` 那一级。只有把手动喂帧与真实帧分开，降级阶梯才可复现。

**`enabled=false` 的行为**：页面不创建 governor，直接固定 `startTier` 一档。基线截图与 A/B 对照必须走这条路径——档位漂移会让基线不可复现。

**F1 清单**：`R1 / G1 验证清单` 新增一行，显示「档位 / 渲染分辨率 / EMA 帧时间 / 粒子数」，即 `档位 high · 渲染 1920×1080 · 帧 17.9ms · 粒子 139/420` 这一形态（未采样时帧时间显示 `—`，不渲染成 0.0）。

## 实现与回归

**分层**（与 §4.155 的遭遇导演同一纪律：纯逻辑可 Node 测，页面只接线）：

- `js/tank_perf.js` 上半段是 R0 的性能采样器（`summarizeMs` / `createPerfRing`），本轮**原地扩写**下半段：`createGovernor` / `updateGovernor` / `getTierConfig`（帧时间 EMA + 升降级门控），无 DOM 依赖，Node 可直接测。**没有新建文件**。`getTierConfig` 返回六键：`resolutionScale` / `particleCap` / `dustIntervalS` / `maxShells` / `staticRebuildIntervalS` / `name`（`scripts/test-perf.js` 有 `Object.keys` 精确相等断言锁住该契约）。
- `tank_3d.html` 只做三件事：① 把 `resolutionScale` 落到 canvas（`applyRenderScale`）② 按档位裁粒子/炮弹/扬尘（`addParticle` 的 cap、`shellCap`、`dustIntervalS`）③ 节流静态几何重建。
- 数值唯一口径 `RULES.perf`（`js/tank_rules.js:1061`，每个键带 rationale 注释）；页面不写死任何阈值。

**回归**：

- `scripts/test-perf.js` 68 条断言（本批 48 条，G1 段 ⑨~⑰：稳定帧不降 / 持续超预算逐级降 + deck 封顶 / 富余逐级回升不跳档 / 抖动抑制 / `minTierHoldSeconds` 锁定 / 异常 dt 忽略 / 参数消费哨兵 / 三档单调性与契约字段；后续补 5 条 `staticRebuildIntervalS` 档位化：三档取值合法 / 随档位单调不减 / high 锁定 0.25 / `Object.keys` 六键精确相等 / 哨兵改 `0.11` 立刻生效）。该文件此前已登记 `run-tests.js` 的 `TESTS`，本轮沿用。
- `scripts/test-browser-perf.cjs` 是**浏览器第八链**，测页面接线：档位真的改画布尺寸了吗、粒子/炮弹真的被裁了吗、降级后还能开车开火吗。
- 基线按档拆成三份（分辨率不同像素网格不可比，**必须分档**）：`baseline.json`（720p）/ `baseline-1080p.json`（1920×1080 + `perf=manual`）/ `baseline-deck.json`（1280×800 + `tier=deck` + `perf=manual`），输出在 `tmp/render-baseline3d/`（不入库）。`npm run baseline:3d --all` 一次跑三档，新增 `npm run baseline:3d:all` 作同义入口。

**验证记录（2026-10-28）**：`npm run check` EXIT=0；`npm test` 69 通过 / 0 失败；`npm run test:browser` 八链全绿；`npm run baseline:3d --all` 三档 PASS（mean=0 max=0）。

## 沿革

- **2026-10-28（§4.157，ISSUES #AB1）**：基准分辨率由固定 1280×720 改为**跟随视口**（含像素预算与 resize 重算），修掉 16:10 / 3:2 / 超宽屏上的画面拉伸；`?w=&h=` 语义收窄为「钉死尺度」并用于基线可复现。

- **2026-10-28 `staticRebuildIntervalS` 进档位表**：原实现三档共用一个固定 0.25s，文档当时只能写「未进档位表、不是已实现的档位差异」。现补为 `high` 0.25 / `mid` 0.40 / `deck` 0.60，`getTierConfig` 返回六键，`test-perf.js` 63 → 68 条（新增档位取值 / 单调性 / high 锁定 / 契约六键 / 哨兵生效）。
- **2026-10-28 F1 开关判定修复（既有缺陷）**：原实现读内联 `style.display`（初始为空串，实际可见性由 CSS 决定），判定条件永远不成立——当前布局「默认可见」下恰好等价，但只要默认改成隐藏就会退化成「按两次才出来」。已改为 `getComputedStyle(el).display === 'none'`。
