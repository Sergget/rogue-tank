## 1. 需求与判据

用户原话（2026-10-23）：「适当研究伪 3d（即 3d 图形 + 2d 交互）」。

拆成两条可验证的判据：

1. **3D 图形**——画面要有可读的**体积**：物体有高度、有朝向一致的受光与投影、遮挡关系符合透视直觉。**不等于**必须用 3D API 渲染。
2. **2D 交互**——所有输入与判定仍落在**世界 XY 平面**：鼠标拾取 = `screenToWorld`、命中 = 多边形射线、移动 = 二维速度积分。玩家永远不需要操作第三个轴。

只要满足这两条，玩家读到的就是「伪 3D」。**关键约束**：一旦高度开始影响玩法（例如越肩射击、地形高低差加成），「2D 交互」这条判据就会被破坏——这是本页最重要的分界线（§2.2）。

## 2. 现状盘点（2026-10-23 实测）

### 2.1 已有的 2.5D 视觉基础（可直接复用）

| 手段 | 实现位置 | 现行效果 |
|---|---|---|
| 部件侧壁 | `js/tank_battledraw.js` `drawPartSideWall`（:1522） | 轮廓按**世界光反向**偏移后实心填充、顶面覆盖，只露背光侧窄带 ⇒ 读作高度 |
| 车底影 | `drawTankGroundShadow`（:1495） | 两层椭圆，形状随车体转、偏移不随车体转 |
| 炮塔座圈凸台 | `drawTurretRing`（:2158） | 右下偏移暗环 + 顶面 + 受光描边，炮塔「坐」在车体上 |
| 顶面轮廓光 | `drawTankRimLight`（:1542） | 左上暖白 1.1px 渐变，与暗勾线形成一明一暗 |
| 树冠体积 | `js/tank_assets.js` `bakeCanopy` | 球面体积渐变 + 左上受光团 + 右下暗冠缘 |
| 岩石多面体 | `bake` 的 `rock-poly` 分支 | 逐边法线着色 + 侧壁 + 棱边高光 |
| 建筑背光墙 | `drawCover` 的 `box` 分支 | 右下偏移体块，屋顶盖住其余部分露出 2~3px 墙体 |
| 抛射弹的「高度」 | `js/tank_fire.js` `drawShells` | 抛物线用 `z = sin(p·π)` 抬升 + 地面椭圆投影（纯视觉） |

**结论**：视觉层面的「3D 图形」已经有相当基础；缺的不是「再加一层阴影」，而是**统一的高度模型**与**遮挡排序**。

### 2.2 高度目前不参与玩法（关键事实）

- `getPartZRange`（`js/tank_geometry.js`:18）返回**固定常量**：车体 0~1.4、炮塔 1.4~2.3。`RULES.heights` 已于 2026-09-20 #E3 删除，注释明确写着「车高数值是死数据」。
- 命中判定 `raycastTank` / `bestTankHit`（`js/tank_geometry.js`:81 / :139）是**纯 2D 多边形射线**，没有 z。
- 视线 `hasLineOfSight`（`js/tank_cover.js`）判的是 tier 的 `vision` 布尔，不是几何高度。
- 炮塔高度只用于 `getExposure` 的单一二值阈值（`zMin >= 1.2`），实际只区分「车体/炮塔」。

⇒ **现行「2.5D」是画出来的，不是算出来的**。这正是伪 3D 路线可以低成本推进的原因，也是它的天花板所在。

## 3. 三条候选路线（对比）

| 路线 | 做法 | 3D 图形达成 | 2D 交互 | 工作量 | 判定 |
|---|---|---|---|---|---|
| **A. 强化现有 2.5D 绘制** | 在现有 Canvas 2D 上补：统一高度表、遮挡排序、侧壁宽度按高度派生 | 中（体积可信，但相机不能转） | **完全保持** | 小（2~4 人日） | ✅ **推荐作为第一阶段** |
| **B. 伪 3D 投影层** | 世界仍是 2D，渲染时做一次固定斜投影/等距变换（`worldToScreen` 前乘一个 3×3 仿射） | 中高（有明确高度感与纵深） | 保持（反向变换回平面即可） | 中（8~15 人日，含拾取反解与所有绘制层校准） | ⏸ 可作为第二阶段，需先做 1× 尺度可行性预研 |
| **C. 真 3D（WebGL/Three.js）** | 引入 3D 渲染器，地形/单位建 mesh，相机可转 | 高 | 需射线打到地面平面 | 大（重构渲染层，≥1 个月） | ⏸ **本阶段不做**（成本高、收益未证实）；**技术路线未被排除**，见 §3.1 |

> **若目标是「更好兼容视野-隐蔽」，路线选择不同**：本页的推荐（A）只针对「提升体积感」。因为视野-隐蔽依赖**高度进入遮蔽判定**，结论变为推荐 **B**，且要先补现行判定的三个结构性缺陷。见 [视野-隐蔽与伪 3D 兼容性](./vision-stealth-3d-compat.md)。

### 3.1 「零依赖 / `file://` / Node 像素回归」是**当前状态**，不是硬约束

> **2026-10-24 用户纠正**：「零依赖 + file:// 直开 + Node 像素回归不要作为硬约束，只是目前状态的临时的选择。」

这条纠正推翻了本页初版（2026-10-23）的第 1、2 条「不选 C」理由。**三条都只是现阶段的工程选择**，随项目阶段可变：

| 现状 | 事实 | 性质 |
|---|---|---|
| 零运行时依赖 | `package.json` 无 `dependencies`，页面按序加载全局脚本、无打包步骤 | **临时选择**。若真 3D 值得做，引入 Three.js + 打包是允许的成本 |
| `file://` 直开 | 页面走 dev server（`npm start`）才正常；`tools/bake.html` 是唯一刻意支持 `file://` 的页面 | **临时选择**。若引入 WebGL，`file://` 能力可以放弃 |
| Node 像素回归 | `test-render.js` 借 `scripts/lib/mini-canvas.js` 做光栅化断言 | **临时选择**。WebGL 可用浏览器端截图回归替代，只是需要重建回归链 |

**因此对真 3D 的判断改为「成本/收益」而不是「能不能」**：现阶段不做的真实理由是下面四条（缺美术管线、玩法收益未证实、需要重建回归链、阶段策略），而**不是**架构禁令。若将来用户明确要可旋转相机或等距视角，路线 C 是**可选项**，只需接受重建渲染层与视觉回归链的代价。

**现阶段仍不推荐 C 的理由**（按权重排序）：

1. **美术管线不存在**：项目无 3D 资产（模型/贴图/骨骼），已明确否决 AI 出图（§5）。真 3D 会立刻撞上「没有美术来源」的墙——这是**最硬**的一条，且与渲染技术选择无关。
2. **玩法收益未证实**：本作是俯视战术射击，玩家目前不需要转相机；3D 的主要卖点（自由视角、纵深）在此玩法里尚未证明能换回 ≥1 个月的重构成本。
3. **回归链要重建**：现有视觉回归是 Node 侧真实光栅化逐像素断言（29 + 9 项）。换 WebGL 后这套断言无法直接运行，必须改用浏览器截图基线——**可做，但属于额外成本**，不是「做不到」。
4. **阶段策略**：路线 A 能以 2~4 人日拿到「体积感」的主要收益，且**不为将来的 3D 关门**（绘制层与命中/交互本就分离，见 §1 的判据）。先用 A 验证「体积感是否真的提升观感」，再决定是否投入 C，风险更低。

## 4. 推荐路线 A 的具体方案（未落地）

### 4.1 统一高度表（唯一口径）

现状高度散落在多处字面量（侧壁偏移 4.0/5.2、2.3/3.1、座圈偏移、树冠半径 1.4×）。建议收口为**一张单位高度表**：

```
RULES.heights2p5d = {
  tank:  { hull: 1.0, turret: 0.75, barrel: 0.25 },   // 车体/炮塔/炮管的相对高度（单位：车体高）
  cover: { wall: 1.2, tree: 3.0, rock: 1.8, building: 4.0 },
  light: { dx: 0.55, dy: 0.75 }                        // 世界光方向（现行：右下）
}
```

**只驱动渲染**：侧壁像素宽度 = `height × pxPerUnit`、投影偏移 = `height × lightOffset`。**不进入命中与视线**（那条线一旦破了 §1 的第 2 条判据）。

> ⚠ 该表**尚未存在**，属本页设计建议；实施时归 `role-systems`（`RULES` 唯一写者），消费方是 `role-render-fx`。

### 4.2 遮挡排序（当前最大的可感知缺陷）

现状绘制顺序是**按层固定**的：地面 → 掩体（含建筑）→ 坦克 → 炮弹 → 树冠（`tank_battle.html`:6109~6352）。后果：

- 坦克永远画在建筑**之上**，即使坦克在建筑背面 ⇒ 建筑没有「高于坦克」的读感。
- 树冠永远盖在所有坦克之上（这是**刻意**的视线遮挡，但同一棵树对远近两辆车做同样遮挡，缺少高度差）。

建议引入**按「脚点 y + 高度」排序**的软排序（y-sort）：

1. 每个可绘制体带 `sortY = y + height × k`（k 为世界光方向的 y 分量）。
2. 只在**同一 ground band** 内排序；贴地平面（road/mud/water）保持早绘。
3. 树冠层拆成「树干（参与排序）+ 冠（始终覆盖）」两段，避免树冠排序后遮挡错误。

**风险**：现有测试用固定绘制顺序做像素断言，排序改动会让多项断言漂移（见 §7）。

### 4.3 侧壁宽度按高度派生

现行 `drawPartSideWall` 的两层偏移是硬编码（车体 4.0/5.2 与 2.3/3.1、炮塔薄一档）。改为 `height × k` 之后：重坦侧壁**自然**比轻坦厚，不需要按车写死。这是**最小的可见收益点**，也是最容易先做的一步。

### 4.4 与像素对齐的兼容性

`renderCamPos`（`js/tank_camera.js`:186）把相机量化到 `1/zoom` 整数倍以消除地面纹理抖动。**任何新增的高度偏移都必须是 `1/zoom` 的整数倍**，否则侧壁会在移动时闪烁——这是本路线最容易踩的坑，实施时必须补回归。

## 5. 与资产口径的关系（2026-10-23 裁定）

- **程序化生成是唯一实机路径**（`js/tank_paint.js` + `js/tank_assets.js` 的 `bake`）。
- **后期贴图接线保留**：把 PNG 放到 `assets/<key>.png` 即接管同一接口（`drawAsset` / `drawTankSprite`），锚点与画布尺寸基准由 `tools/cover-refs.json` 给出，落盘后用 `scripts/covers-anchor-check.py` 验收。细则见 [贴图资产与审核标准 · 出图管线](./textures.md#出图管线)。
- **AI 出图链已删除**（2026-10-23）；现有坦克 PNG 已删除，`assets/` 仅余 `README.md`。伪 3D 路线 A **不新增任何图片资产**——它只改程序化绘制与排序。
- 若将来走路线 B（斜投影），**必须先按 1× 实机尺寸出图确认**再投入（2026-10-23 教训：放大审美与实机观感系统性脱节）。

## 6. 验收口径建议（实施时）

| 项 | 判据 |
|---|---|
| 高度一致性 | 同一单位在任意角度下，侧壁像素宽度恒定（世界固定光）——现 `test-render.js` ⑧ 已锁方向，需扩到宽度 |
| 遮挡正确性 | 坦克在建筑背面时，建筑的可见部分必须覆盖坦克；构造 4 个方位断言 |
| 相机闪烁 | 移动 12 帧、3 个 zoom 下侧壁采样点色差 = 0（沿用 `renderCamPos` 的判据） |
| 玩法不变 | `resolveHit` / `hasLineOfSight` 的输出与改动前**逐字节一致**（哈希断言）——证明高度只管渲染 |

## 7. 风险清单

1. **测试重锚**：`test-render.js` 的 ⑧a/⑧b、`test-covers.js` 的投影断言、`test-batch5-combat.js` 的 wall 段都依赖现行绘制顺序与偏移常量，排序改动会红。**先写新断言再改实现**（TDD）。
2. **性能**：y-sort 让全量可绘制体每帧排序（covers 700~1100 在 strip 节点）。需要空间分桶 + 只排视口内，参考 `GROUND_CACHE` 的视口过滤做法。
3. **与树冠刻意遮挡冲突**：树冠「盖住坦克 = 视线遮挡」是**设计意图**（`drawFoliage` 注释明确）。改成 y-sort 会破坏它，必须先裁定「树冠是否参与排序」。
4. **伪 3D 的天花板**：路线 A 无法解决「相机不能转」，若后续用户要等距/斜视，仍须走路线 B。**不要为了 A 的整洁去重构相机**。
5. **高度表落地依赖 `role-systems`**：`RULES` 只有一个写者（`AGENTS.md` §3.6），本页的表只是**提案**，不是现行配置。

## 8. 结论

- **可做，且第一阶段成本低**：路线 A 复用现有侧壁/方向光/投影，只补「统一高度表 + 遮挡排序 + 侧壁按高度派生」，不碰玩法、不加资产，也不需要引入第三方库。
- **真 3D（路线 C）本阶段不做，但不是禁区**：零依赖 / `file://` / Node 像素回归三条都是**当前临时状态**（2026-10-24 用户纠正），不构成架构约束。真正拦路的是**缺美术管线**与**玩法收益未证实**；若将来确需可旋转相机，接受重建渲染层与回归链的代价即可走 C。
- **本页是设计预留**（用户 2026-10-23 选择「仅研究文档」），**代码尚未改动**。实施前必须先补 §6 的验收断言，并按 `AGENTS.md` §2.2 走完整 4 步生命周期。
