## 1. 「没有建模基础」的真实影响（先回答最担心的）

**结论：对本作而言这是一个伪约束。** 原因不是「可以学建模」，而是**本作根本不需要手工建模**——全部场景元素是硬表面参数化几何，且**已经以数据形式存在于仓库里**：

| 元素 | 现存数据（实测） | 3D 化方式 | 需要建模吗 |
|---|---|---|---|
| 坦克车体 | `tanks/*.json` 的 `hull.verts`（tiger-I：9 顶点箭形多边形） | 挤出成棱柱（顶面 = 现多边形，侧壁 = 高度） | ❌ 顶点已在 `tank_designer.html` 里编辑 |
| 坦克炮塔 | `turret.verts`（tiger-I：23 顶点） | 同上挤出 | ❌ 同上 |
| 炮管 | `barrel.len/width/muzzle/jacket/mantlet`（参数化） | 圆柱 + 参数化附件 | ❌ 纯参数 |
| 掩体/墙/楼 | `covers[].x/y/w/h/angle`（OBB） | **盒子**——最简单的 3D 图元 | ❌ 一个 BoxPrimitive |
| 树木/灌木 | w/h + `blobPath` 波浪轮廓（确定性函数） | 圆柱干 + 波浪轮廓挤出冠 | ❌ 程序化 |
| 岩石 | `rock-poly` 多边形 | 多面体（2D 绘制**已经**是逐边法线着色的伪多面体） | ❌ 程序化 |
| 地面 | biome 纹理烘焙（`_paintGroundTexture`） | 平面 + 现有纹理 | ❌ 零高度平面 |
| 涂装/迷彩 | `tank_paint.js` 的 `TEXTURE_DEFS` 程序化烘焙 | 顶面贴现烘焙纹理、侧壁贴明暗条带 | ❌ 已是程序纹理 |

**「建模基础」真正挡住的是什么**：手工雕琢的高细节资产（铆钉、防滑纹、角色、有机形体）。本作**没有**这类需求——现行的 2D 视觉本身就是程序生成的，3D 化只会换一种程序生成方式。

**真正缺的是技能而不是资产**：

| 路线 | 需要的新技能 | 现有基础 | 补齐成本 |
|---|---|---|---|
| P1（补判定）+ A（2.5D 绘制） | 无 | 已具备 | 0 |
| B（固定斜投影） | 2D 仿射/剪切矩阵（~50 行数学） | `utils` 已有 `rotate/angDiff` | ~1 人日 |
| C（真 3D） | 渲染器 API（Three.js 或 WebGL）+ mat4 + 光照材质 + 性能调优 | 无（但 `playwright` 回归链已具备） | **+5~8 人日学习曲线**（叠加在 ≥1 个月实现上） |

> **判据**：如果一条路线的资产可以**全部由现有 JSON/配置驱动生成**，它就不受「无建模基础」约束。A/B 完全满足；C 在「参数化挤出」路线下也满足——只有追求「美术精修模型」时才需要建模，而那是可选增强，不是门槛。

## 2. 影响面清单（按路线 × 受影响系统，2026-10-24 实测）

### 2.1 P1：补视野-隐蔽判定三洞（纯 2D，见 [vision-stealth-3d-compat](./vision-stealth-3d-compat.md)）

| 受影响 | 影响 | 量级 |
|---|---|---|
| AI 行为 | 灌木不再绝对隐蔽 ⇒ 潜伏打法削弱；墙体车体/炮塔分级 ⇒ hull-down 战术成立 | 平衡性重调 |
| 测试 | `test-covers.js`（`hasLineOfSight` 大量断言）、`test-ai.js`（LoS 门控）、`test-browser-r4.cjs` F3 段需重锚 | 中 |
| `RULES` | 新增 `coverTiers[*].height`（role-systems 唯一写者） | 小 |
| 渲染 | **零**（这是它作为第一步的价值） | 0 |

### 2.2 路线 A：强化 2.5D 绘制

| 受影响 | 影响 | 量级 |
|---|---|---|
| `tank_battledraw.js` | 侧壁宽度按高度派生、y-sort | 小~中 |
| `test-render.js` | ⑧a/⑧b 等**像素断言漂移**（全文件 91 条 `ok()`，视觉断言约占三分之一） | 中 |
| 输入/拾取 | **零**（投影不变） | 0 |
| 小地图/HUD | **零** | 0 |

### 2.3 路线 B：固定斜投影层

| 受影响 | 影响 | 量级 |
|---|---|---|
| 世界变换 | 单点插入：`tank_battle.html:6045-6048`（`translate+scale` 一处）——**绘制代码不用改**，投影在 ctx 层生效 | 小 |
| **拾取/输入** | `worldToScreen/screenToWorld` 全仓 **16 处**（battle 9 / camera 4 / ai_squad 1 / drone 1 / bench 1）需反向仿射；鼠标→地面平面仍可逆（固定投影保双射） | **中（最大工作面）** |
| **地面烘焙缓存** | `drawGroundCached` 假设「可见世界 = 相机周边 AABB」（`wantW = vw + 2×MARGIN`）；斜投影下可见区是**平行四边形**，AABB 缓存要么放大冗余、要么改分带烘焙 | **中~大（最大技术风险）** |
| HUD/威胁指示 | 屏幕锚定元素（血条、`threatIndicators` 视口外来袭方位）需按新投影换算 | 小~中 |
| 小地图 | **零**（俯视 2D 逻辑与本页正交） | 0 |
| `test-render.js` | 像素基线**整体失效**（mini-canvas 画的是同一套 ctx 调用，可跟随投影，但所有基线图重录） | 中 |
| 玩法 | 距离/方向判读变难（纵深压缩）——**与视野-隐蔽的「判读距离」需求相悖**，需 HUD 补偿（§4.4 of vision-stealth） | 设计项 |

### 2.4 路线 C：真 3D

| 受影响 | 影响 | 量级 |
|---|---|---|
| 渲染层 | 整体重写（`tank_battledraw/tank_assets/tank_fx/tank_paint` 的绘制路径）；逻辑层（命中/AI/移动）**不动**——这正是当初「2D 交互」分层的红利 | 大 |
| 输入 | `screenToWorld` 改为射线↔地面平面求交（数学 10 行） | 小 |
| **回归链** | `mini-canvas`（纯 JS Canvas2D 垫片）**无法跑 WebGL** ⇒ 91 条像素断言整体退役，改浏览器截图基线（见 **I3**） | **大（流程变革）** |
| 地面/性能 | 地面烘焙层被 GPU 网格取代；帧预算从「ctx 调用数」换成「draw call / 填充率」，需重新标定 | 中 |
| 小地图/HUD | 小地图不动；HUD 屏幕锚定不动 | 0 |
| 设计器 | **不动**——`tank_designer.html` 编辑的 `verts` 就是 3D 挤出的源（§1 表） | 0 |

### 2.5 与伪 3D 无关但会被牵动的基础事实

- `camouflageFiringMul` 读 `performance.now()`（`tank_cover.js:313`）——**任何**视觉路线都可能放大确定性风险（回放 hash），应先行修（I0）。
- 存档兼容：`coverTiers.height` 是新增键，旧存档缺省走兜底（`#W16-②` 先例：缺键不抛错）。
- 单机无网络同步 ⇒ 无多人一致性影响。

## 3. 基础设施清单（先行工程，按依赖排序）

> 原则：**每一项都独立可验证、独立可回退**，且在最终选定的路线上**不报废**。

| # | 基础设施 | 内容 | 量级 | 解锁什么 |
|---|---|---|---|---|
| **I0** | **模拟时钟** | 全游戏统一 `simNow`（主循环逐帧注入），迁移**判定/计时路径**的挂钟读取——实测 **13 处**：`tank_ai.js` 2（suspicious 超时/噪声）、`tank_boss.js` 5（减速/冲锋到期）、`tank_cover.js` 1（开火惩罚窗口）、`tank_fire.js` 1（`lastFireAt` 写入）、`tank_model.js` 2（**timed 修饰器 `expiresAt` 全部读 `Date.now()`**）、`tank_entity.js` 1。**豁免**：`tank_economy.js` 存档时间戳（本就该用墙钟）与渲染侧 fx 时间量子（纯视觉） | 1~1.5 人日 | 确定性回放、P1 的开火惩罚窗口可测；顺带修复「全部 timed buff 实为非确定性」的存量隐患 |
| **I1** | **高度数据模型** | `RULES.coverTiers[*].height`（18 键分档表，建议值见 [vision-stealth-3d-compat §4.1](./vision-stealth-3d-compat.md)）+ 车体/炮塔真实高度字段化（替代 `getPartZRange` 硬编码 0~1.4/1.4~2.3）。**唯一口径**，渲染与判定同读 | 1 人日 | P1、A、B、C 全部（这是共同地基） |
| **I2** | **统一遮蔽查询** | `hasLineOfSight` 从布尔改高度分档，与 `getExposure` 的 `zMin>=1.2` 同源；`vision` 键保留为「是否参与」开关 | 2~3 人日 | P1 落地；烟雾是否入档先裁定 |
| **I3** | **视觉回归双轨** | ① 现有 `mini-canvas` 像素链保留（A 可用）；② 新增**浏览器截图基线链**：复用 `playwright-core` + 现有四条 `test:browser` 框架，固定 seed/视口/步数截图 + 容差比对 + 基线入库 | 2~3 人日 | B/C 的前置；也是以后任何视觉改动的保险 |
| **I4** | **拾取反解层** | `worldToScreen/screenToWorld` 收口为唯一模块（现散在 16 处调用但实现已在 `tank_camera.js` 单点——补投影参数与逆变换） | 1 人日 | B 的前置；C 直接换射线求交 |
| **I5** | **几何挤出工具**（可选，仅 C 需要） | `verts → 棱柱网格`、`barrel 参数 → 圆柱`、`w/h/angle → 盒`、`blobPath → 冠体` 的参数化生成器 + `tools/bake.html` 式预览页 | 3~5 人日 | C 的「零建模」资产管线 |

**依赖关系**：I0 独立 → I1 → I2（P1=I0+I1+I2）→ I3/I4 并行 →（若走 B）投影层 →（若走 C）I5 + 渲染器。

| 路线 | I0 时钟 | I1 高度表 | I2 遮蔽 | I3 截图回归 | I4 拾取 | I5 挤出 | 合计先行 |
|---|---|---|---|---|---|---|---|
| P1 补判定 | ✅ | ✅ | ✅ | — | — | — | **4~5.5 人日** |
| +A（2.5D 绘制） | ✅ | ✅（共享） | — | 建议 | — | — | +2~4 人日 |
| +B（斜投影） | ✅ | ✅（共享） | ✅ | ✅ 必须 | ✅ | — | +8~15 人日 |

> 注意 **I1 是全路线共享的**：先做 P1 的人日不会被任何后续选择浪费——这是「先补判定、再选渲染」顺序的数学依据。

## 5. 建议的先行顺序（最小可逆起步）

1. **I0 + I1 + I2（= P1，4~5.5 人日）**：不动渲染、不动输入，收益立即可玩（灌木≠楼房、hull-down 成立、隐蔽对称化可选）；顺带把 13 处挂钟读数收敛成模拟时钟，消除存量非确定性。
2. **I3 截图基线链（2~3 人日）**：与 1 并行可做；做完后**任何**视觉实验都有保险，值得在动渲染前完成。
3. **A（2~4 人日）**：共享 I1 高度表，验证「体积感是否真提升观感」——便宜的决策实验。
4. **B 的 Go/No-Go 门**：以「玩家能否在斜投影下判读 650px 级距离」做 1× 实机预研（先画 3 张静态对比图，1 人日）再决定，避免 8~15 人日押注在未验证的判读性上。
5. **C 仅在**「可旋转相机」成为明确玩法需求时启动 I5。

## 6. 风险与未决

1. **B 的地面缓存重构**是隐藏最深的成本（平行四边形可见区 vs AABB 缓存），预估 2~4 人日未计入上表。
2. **I3 截图基线**在 CI（GitHub Actions ubuntu）上跑无头浏览器已具备先例（`test:browser` 本地跑、CI 未挂）——若要进 CI 需另配。
3. **`test-render.js` 91 条断言**在 B/C 下大量退役，需要「哪些迁截图、哪些删」的逐条裁决——建议做一张映射表再动手。
4. 高度表数值（vision-stealth §4.1）是**提案**，落地前需 role-systems 按平衡实测标定。
5. 「玩家可被 AI 偷袭」（隐蔽对称化）是**玩法裁定**而非工程项——会显著改变难度曲线，应单独问。

## 7. 一句话回答

> **「没有建模基础」不构成障碍——本作全部几何已是参数化数据（多边形顶点/OBB/参数），三条路线的资产都能由现有 JSON 驱动生成。真正要先做的是 4~5.5 人日的判定地基（I0 时钟 + I1 高度表 + I2 统一遮蔽）和 2~3 人日的截图回归保险（I3）；渲染路线（A/B/C）可以在这些地基之上随时启动或放弃，不浪费任何投入。**
