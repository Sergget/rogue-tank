## 结论先行

**推荐路线 B（固定斜投影 / 等距层）。** 理由不是「3D 更好看」，而是：

> **视野-隐蔽本质上是一个「谁挡得住谁的视线」的几何问题，而现行实现把它压成了「2D 距离 × 布尔」。** 谁的路线能把**高度**带进遮蔽判定，谁才真正兼容这套机制。

- **路线 A（强化 2.5D 绘制）**：只改画面，几何判定完全不动 ⇒ **对视野-隐蔽零改善**，且会让「画得有高度、判定没高度」的割裂更强（看得见一个高建筑却挡不住视线、或反过来）。可作为**过渡**，但**不解决本问题**。
- **路线 B（固定投影）**：世界仍是 2D 平面，但渲染引入**高度轴**，可建立 `height` ↔ 屏幕遮挡的映射 ⇒ 能以**中等成本**让视野-隐蔽获得真实高度语义（见 §4）。
- **路线 C（真 3D）**：最彻底，但视野-隐蔽**不是**现在该由它来解决的问题（见 §5）——机制本身的缺陷用 2.5D 就能修，先上 3D 属于「用大炮打蚊子」。

**但必须先说清楚：真正的瓶颈不在伪 3D 路线，而在现行机制本身的三个结构性缺陷（§2）。** 无论选哪条路线，这三个洞都要补。

## 1. 现行机制的完整数据流（2026-10-24 实测）

### 1.1 「敌人看得见玩家」的判定链

```
aiDecideEnemy（js/tank_ai.js:697）
  enterDCamo = triggerDist(700) × camouflageDistanceMultiplier(玩家)   ← 仅 1 次乘法
  los        = hasLineOfSight(敌, 玩家)                                ← 布尔
  canSee     = (!needLoS || los) || lastKnownPlayerPos
  激活 = dist <= enterDCamo && canSee
```

**只有两个输入：圆形距离 + 一个布尔。** 没有视线方向、没有观察者朝向、没有高度、没有遮挡比例。

### 1.2 「谁挡视线」的判定（`js/tank_cover.js:1036`）

```js
function hasLineOfSight(ox,oy,tx,ty, coversList){
  for(const h of hits){
    const tier = COVER_TIERS[h.cover.tier];
    if(tier && tier.vision) return false;   // :1040 —— 命中即全遮，无高度、无距离衰减
  }
  if(smokeBlocksLoS(ox, oy, tx, ty)) return false;
  return true;
}
```

**`vision: true` 是一个布尔**，18 个 tier 里 10 个为 true（含 `bush` 灌木、`tree`、`wall`、`full`、`building`、`rock`）。灌木和楼房在视线判定里**完全等价**。

### 1.3 隐蔽值（`js/tank_cover.js:346`）

```js
camouflageValue = baseCamo[吨位] × motionMultiplier[运动] × firingMul + terrainBonus
```

**是一个与位置无关的标量**：不看玩家在谁的视线里、不看朝向、不看离遮挡物多远。

### 1.4 关键实测数据

| 项 | 值 | 说明 |
|---|---|---|
| `RULES.coverTiers` 带高度字段的键 | **0 / 18** | 没有任何 tier 有 `height` |
| `RULES.heights` | **不存在**（2026-09-20 #E3 删除） | 高度体系已整体移除 |
| `getPartZRange` | 固定常量：车体 0~1.4 / 炮塔 1.4~2.3 | 唯一"高度"，且只有「过不过 1.2」一个阈值 |
| `aiSpotBaseDist` | 650 px | **实测零消费方**（只在 `tank_rules.js:51` 定义 + 测试断言里出现） |
| `alertLevel === 2`（alert/友邻遇袭） | **实测零消费方** | `tank_ai.js:115` 注释声明五层级，但代码只用到 0/1/3 |

## 2. 现行机制的三个结构性缺陷（无论选哪条路线都要修）

### 2.1 缺陷一：灌木 = 楼房（`vision` 布尔吞掉了高度）

`hasLineOfSight` 命中任一 `vision:true` 的 cover 就 `return false`。后果：

- **躲在灌木后 = 躲在楼后**，同样的绝对隐蔽；
- **高建筑挡不住「从它旁边过」的视线**（只看有没有相交，不看是否真的挡住）——这正是「画面上明明被挡、却被点亮」的来源之一；
- **掩体高度差完全消失**：蹲在矮墙后和蹲在楼后没有区别。

### 2.2 缺陷二：隐蔽值与几何无关（地形加成是「站在格子里」）

`camouflageTerrainBonus` 用 `getCoverUnderTank(t)` —— **车体 OBB 与 cover 相交**即算「在灌木里」，加 `bushBonus 0.40`。后果：

- 贴着灌木边缘（视觉上完全暴露）与灌木正中，加成相同；
- **与是否有视线无关**：敌人在正前方 50px 直视你，你依然拿到满额隐蔽加成；
- 隐蔽值**不随距离变化**——同一丛灌木，100px 和 900px 处效果一样。

### 2.3 缺陷三：只有玩家一侧有隐蔽（不对称）

`camouflageDistanceMultiplier(p)` 只在 `aiDecideEnemy` 里对**玩家**取值（`tank_ai.js:694`），**敌人对玩家没有任何隐蔽值**。后果：

- 玩家永远能「看见」所有敌人（视野系统已退役，全屏幕渲染，见 [视野与镜头](../combat/camera-vision.md)）；
- **偷袭只能单向成立**——玩家可以藏，AI 不能藏；
- HUD 上没有任何「我是否暴露」的反馈（没有暴露度指示器）。

### 2.4 附带发现（建议单独处理，不属本页范围）

| 发现 | 证据 | 性质 |
|---|---|---|
| `aiSpotBaseDist` 是死配置 | 全仓仅 `tank_rules.js:51` 定义 + `test-recent-mods.js:83` 断言非零 | 应删或接上消费方 |
| `alertLevel === 2` 从未被写入 | `tank_ai.js` 只有 0/1/3 三态 | 注释与实现不符 |
| 开火惩罚用挂钟时间 | `camouflageFiringMul` 读 `performance.now()`（`tank_cover.js:313`） | **破坏确定性**，`test-replay` 的 hash 基线有理论风险 |

> 这三条属「已核实」，若要修应走 `docs/ISSUES.md` 的 4 步生命周期。本页只登记，不改码。

## 3. 三条路线的兼容性对比

评分口径：**能否让「高度」进入遮蔽判定**（0 = 完全不能，3 = 直接可用）。

| 维度 | A. 强化 2.5D 绘制 | B. 固定斜投影层 | C. 真 3D |
|---|---|---|---|
| **高度进入视线判定** | ❌ 0（几何完全不动） | ✅ 2（世界仍 2D，但渲染有高度轴，可反推遮挡） | ✅ 3（原生有 z） |
| **灌木 vs 楼房可分** | ❌ 仍是布尔 | ✅ 需按高度分档（如 <1.5m 只挡车体、>3m 全挡） | ✅ 天然可分 |
| **观察者朝向 / 视锥** | ⚠️ 1（2D 可加，但与画面无关联） | ✅ 2（与投影方向一致） | ✅ 3 |
| **玩家「被点亮」反馈** | ❌ 画面上无从表达 | ✅ 可用高度差画遮挡指示 | ✅ 最直观 |
| **改动成本** | 2~4 人日 | 8~15 人日（+视野改造 3~5 人日） | ≥1 个月（+视野改造 5~10 人日） |
| **风险** | 低，但**收益也低** | 中（拾取反解、全绘制层校准） | 高（渲染层+回归链重建） |
| **对本文题的净收益** | **≈ 0** | **高** | 最高，但**过度** |

### 3.1 为什么 A 不解决问题（重要）

路线 A 的原始卖点是「用 2~4 人日拿到体积感」。对**视野-隐蔽**而言这个卖点不成立：

- 视野-隐蔽判定读的是 `covers` 的 tier 布尔、`getCoverUnderTank` 的 OBB 相交、一个标量隐蔽值 —— **路线 A 一行都不改这些**；
- 更糟的是 A 会**加剧**现有割裂：画面上建筑有 4m 高、坦克 1.4m 高，但判定里「灌木挡住视线」和「楼房挡住视线」完全相同。**玩家越能看出高度，就越不能接受判定忽略高度。**

### 3.2 为什么 B 是拐点

路线 B 引入固定斜投影后，渲染侧**必须**维护一个高度轴（否则画不出立体）。这带来一个关键副产品：

> **同一份高度数据可以同时驱动「画多高」和「挡多少视线」。**

具体地，把 `height` 加进 `coverTiers` 后：

- 渲染：`screenY = worldY - height × k`（B 的核心公式）；
- 视线：`hasLineOfSight` 从布尔改成**按高度分档**——`height < 1.5` 只挡车体（`zMin` 判定）、`height ≥ 3` 全挡。**两者读同一个 `height`，不会漂移。**

这是 B 相对 A 的**唯一但决定性**的优势。

## 4. 若选 B：视野-隐蔽的最小改造清单（设计，未落地）

### 4.1 给 coverTiers 加高度（唯一口径）

```js
// RULES.coverTiers[*].height —— 单位：米，仅用于「视线遮挡分档」与「投影抬升」
bush:    1.2   // 只挡车体（zMin < 1.2 时遮挡）
wall:    1.4   // 同上（车体藏、炮塔露，与 getExposure 的 zMin>=1.2 同口径）
stump:   0.8   // 不挡视线
rubble:  0.6   // 不挡视线
fallen:  1.0   // 挡车体
tree:    6.0   // 全挡
rock:    2.5   // 全挡
building/full/intact: 8.0   // 全挡
ruined:  2.0   // 挡车体 + 部分炮塔
```

**关键纪律：这张表是唯一口径，渲染与遮蔽都读它。** 这正是现行 `vision` 布尔做不到的。

### 4.2 `hasLineOfSight` 改为高度分档

```
挡视线 ⇔ Σ(沿途 cover 的 height) 在观察者→目标连线上「够高」
判据：cover.height >= 观察者视高（炮塔 2.3m / 车体 1.4m）
```

这样：
- 灌木（1.2m）挡不住炮塔视线 ⇒ **炮塔越掩观察**（与 `getExposure` 的既有语义一致）；
- 楼房（8m）全挡；
- **观察者高度参与判定**（现在是常量，B 之后可以有「侦察无人机俯视」这类设计）。

### 4.3 隐蔽值改为「相对遮挡」而非绝对加成

现行 `bushBonus 0.40` 是「站在灌木里 +0.4」。B 之后应改为**依赖视线透过量**：

```
camouflageTerrainBonus = Σ(沿线 cover 的遮挡强度) × 距离衰减
```

好处：贴灌木边缘只拿到部分加成、深处才拿满 —— **与画面一致**。

### 4.4 补齐玩家侧被点亮反馈

有了高度，可画「我是否在敌人视线内」的指示（如敌方视锥的边缘高亮）。这是**玩法可读性**的关键：现行机制玩家完全不知道自己藏没藏住。

### 4.5 敌人也吃隐蔽值（对称化）

`camouflageDistanceMultiplier` 目前只对玩家取值。B 之后可对敌方同样计算，让玩家也能「被偷袭」——但需先有 4.4 的可读性反馈，否则是纯粹的不公平。

## 5. 为什么不直接上路线 C

按 2026-10-24 的纠正，`file://` / 零依赖 / Node 像素回归**都不是硬约束**（见 [伪 3D 研究 §3.1](./pseudo-3d-2p5d.md#31-零依赖-file-node-像素回归是当前状态不是硬约束)）。所以这不是「不能」，是**不该现在**：

1. **视野-隐蔽的缺陷用 2.5D 就能修**：§4 的改造不需要 z 轴渲染，只需要一份高度表 + 分档判据。上 C 是拿渲染重构换一个 2D 数据表就能解决的问题。
2. **C 会同时重写两件事**：渲染层 + 视线判定。一旦出问题，无法区分是渲染错了还是判定错了——**归因成本**远高于分两步做。
3. **C 的真实收益在别处**：自由相机、真实纵深、可旋转视角。这些与视野-隐蔽**正交**——即使上了 C，§2 的三个洞只要不补，依旧是「灌木 = 楼房」。
4. **顺序建议**：先做 A（拿体积感，验证观感）→ 若视野-隐蔽要深化则升级到 B（高度入判定）→ 只有当「可旋转相机」成为明确需求时才评估 C。

## 6. 建议的实施顺序（供裁定）

| 阶段 | 内容 | 依赖 | 预估 |
|---|---|---|---|
| **P1** | 补 §2 的三个结构性缺陷（高度表 + `hasLineOfSight` 分档 + 隐蔽值相对化 + 对称化）**在 2D 下先做** | 无（不改渲染） | 4~5.5 人日（2026-10-24 由就绪度研究修正：模拟时钟迁移实测 13 处，比初估大） |
| **P2** | 路线 A：统一高度表 + y-sort + 侧壁派生（**共享 P1 的高度表**） | P1 | 2~4 人日 |
| **P3** | 路线 B：固定斜投影层（若届时需要更强纵深） | P2 | 8~15 人日 |
| **P4** | 路线 C：仅在「可旋转相机」成为明确需求时 | — | ≥1 个月 |

> **P1 是本文最重要的结论**：视野-隐蔽的改进**不需要等伪 3D**。先补判定（4~5.5 人日，见 [就绪度 §3](./pseudo-3d-readiness.md) 的 I0~I2 拆解），再谈渲染升级。反过来（先做渲染）会得到一个「画面有高度、判定没高度」的割裂版本。

## 7. 风险与未决问题

1. **高度表归谁写**：`RULES` 只有一个写者（`role-systems`，`AGENTS.md` §3.6）。§4.1 的表是提案。
2. **与既有 `getExposure` 的口径冲突**：`getExposure` 已有一套 `zMin >= 1.2` 判据（弹道侧）。新的视线高度表**必须与它同源**，否则会出现「炮弹被挡但视线通过」或反之。这是最容易出错的地方。
3. **`vision` 布尔不能直接删**：18 个 tier 里 10 个为 true，且是旧存档/外部数据的契约。应保留为「该 tier 是否参与视线判定」的开关，高度作为**档位内的细分**。
4. **测试重锚**：`test-covers.js` 有大量 `hasLineOfSight` 断言、`test-ai.js` 有 LoS 门控断言、`test-browser-r4.cjs` F3 断言 `hasLineOfSight` + `engageRequiresLoS` 仍在。改分档会红一批。
5. **未决**：烟雾是否参与高度分档？（现行 `smokeBlocksLoS` 是独立布尔 + 全遮。）建议烟雾保持「全遮」，因为它本就是为破坏视线而设计。

## 8. 一句话回答用户的问题

> **路线 B 更好兼容视野-隐蔽机制**，因为只有它能让「高度」同时驱动画面与遮蔽。但**当前最该做的不是升级渲染，而是先补判定的三个洞**（灌木=楼房、隐蔽值与几何无关、敌人无隐蔽）——这三件事在 2D 下 4~5.5 人日就能做完，且是任何路线的共同前提。
